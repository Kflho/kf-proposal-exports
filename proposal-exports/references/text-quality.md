# 页片与报告的文字规范

> 这份文件管「说什么、怎么说」：页片的标题、要点、口播、图注，申报书与技术方案的段落，
> 实验报告的结构。图和版式在 `SKILL.md` 与 `ppt-deck.md`；机械检查用 `scripts/text_check.py`。
> 仓库 README、用法文档、代码注释不在本文件范围，按 `kf-personal-development` 的 `readme.md`。

## 逻辑骨架

申报书、技术方案、汇报页片共用一条逻辑链，缺一环就补，不靠辞藻填空：

```text
背景 → 现状（别人怎么做、卡在哪）→ 问题（一句可验证）
     → 研究内容（做什么，与研究目标对应）
     → 创新点（和现有做法的差异）
     → 目标（从研究内容分解，可量化）
     → 技术路线（怎么做）
     → 实验（每个目标至少一个实验，先定性后定量）
     → 结论（达到什么、没达到什么、下一步）
```

四条边界：

- **研究内容 ≠ 创新点**：研究内容回答「做什么」，创新点回答「和别人的差别在哪」。两节不能互相改写。
- **目标来自研究内容**：目标编号与任务书对应，不另起一套。
- **每个目标都有实验**：没有实验的目标不写进目标页；写不出的实验说明目标不可验证。
- **数值有出处**：来自实验、公式或任务书；没有出处就标待定，不猜。

## 页片逻辑

1. **先写标题序列**：把每页标题抄成一份清单，只读标题能讲完整个故事。读不通就改标题，
   不靠正文补。
2. **一页一个主张**：答案放标题，证据放正文（图、表、公式），口播解释「为什么」。
3. **标题写结论**：带判断或数字。话题式标题改写成结论式，例：

   | 话题式 | 结论式 |
   | --- | --- |
   | 模型 | C-W 方程开环临界稳定，必须反馈 |
   | 能控性分析 | 只开径向发动机时秩为 3，切向漂移拉不回来 |
   | 结果对比 | 同一组极点下，解耦解把切向推力从 20 降到 1.8 |

4. **目标页与实验页一一对应**：给一张对照表，左列目标编号，右列实验、指标、结论。评审能顺着
   表格找到证据。

## 分体裁规范

### 页片

| 部分 | 写法 | 反例 | 检查 |
| --- | --- | --- | --- |
| 标题 | 一句结论；**≤16 汉字、一行**（超了拆页）；主动语态；带数字 | 「模型」「结果对比」这类话题；20 字以上的整句 | `title-no-verdict`、`title-topic`、`title-too-long` |
| 语体 | 学术表述：可用率下降 / 测距中断 / 仅增加站数无法恢复 | 「掉点」「补不回」「拉满」这类工程口语 | `colloquial` |
| 要点 | 3–5 条；每条一句话、≤40 字；「**粗体引导词**：一句说明」 | 整段论文体；一页塞 8 条 | `too-many-bullets`、`bullet-too-long` |
| 口播 | ≤120 字；能直接念；结论 → 证据 → 所以；不照读页面 | 把页面文字念一遍 | `notes-too-long`，其余人工 |
| 图注 | 指标名 + 口径 + 单位；与图内文字逐字一致 | 只写「如图所示」 | 人工 |
| 表头表注 | 单位进表头；条件进表注；数字对齐 | 单位散在单元格里 | 人工 |

### 申报书与技术方案

| 段落 | 写法 | 反例 |
| --- | --- | --- |
| 背景 | 说清为什么现在做：现状变化、约束、代价 | 从宏大叙事开头，落不到本项目 |
| 研究现状 | 别人做到哪、卡在哪、与本项目的关系 | 罗列文献，不给判断 |
| 问题 | 一句可验证的问题，能对应后面的目标或实验 | 口号式问题，无法验证 |
| 研究内容 | 做什么；与目标、任务书对应 | 把创新点写成研究内容 |
| 创新点 | 与现有做法的差异，给对比维度 | 只说「首次提出」，没有对比 |
| 目标 | 从研究内容分解；可量化；编号对应任务书 | 目标写成愿望 |
| 技术路线 | 每一步怎么做、依据是什么 | 只画流程图，不写依据 |
| 指标 | 指标名、口径、条件、考核方式四件事写全 | 只给数值，不写条件 |
| 实验设计 | 每个目标至少一个实验；先定性后定量 | 实验与目标对不上 |
| 结论与预期成果 | 达到什么、没达到什么、下一步 | 只写成绩，不写限制 |

### 实验报告

按 GB/T 7713.3 的骨架组织，正文至少包含：

- 目的：验证哪个目标；
- 方法：数据、参数、对照；
- 结果：数值与图，标明口径；
- 讨论：与预期或论文的差异，失败原因；
- 结论：达到与未达到，下一步。

### 说明类

- 变更说明、汇报消息：一句结论开头，说清改了什么、影响谁、下一步；
- README、用法文档：不在本文件，按 `kf-personal-development` 的 `readme.md`。

## 去 AI 味

词表和模式在 `assets/text/banned.json`，不在正文逐字列举。规范只描述类别：
起跑式铺垫、意义拔高、宣传语、客服腔、套话收尾、假对比、三段套话、模糊权威、翻译腔。

下面是真实技术句的改法，重点是把「评价」换成「条件 + 数值 + 结论」：

| 空泛写法 | 规范写法 |
| --- | --- |
| 对系统鲁棒性的提升效果较为明显 | 参数摄动 20% 时，跟踪误差从 0.8 m 降到 0.2 m |
| 该方法在工程应用中具备较好的参考价值 | 8 站、100 ms 时延下仍收敛，可直接接现有控制器 |
| 结果验证了方案的有效性与可行性 | 三种工况均未失稳，最大超调 4.2% |
| 从整体上看，方案兼顾了性能与成本 | 同样跟踪精度下，求解时间从 12 ms 降到 5 ms |
| 该问题受到了广泛关注 | 2024 年后有三类做法：集中式、分布式、事件触发；前两类在 8 站以上失稳 |

改完回读：有没有新增信息，条件、范围、否定、归因是否还在。

## 机械检查

```bash
python scripts/text_check.py deck.pptx            # 页片：标题/要点/口播
python scripts/text_check.py report.md            # 报告：标题/句子/禁用词
python scripts/text_check.py deck.pptx --json

python scripts/text_consistency.py --root .            # 仓库文档：术语/标题/相对链接
python scripts/text_consistency.py --root . --exports  # 报告产物：图片链接/图注/图号/孤立图 + AI 腔
```

判据见 `assets/text/banned.json` 与下表：

| 检查 | 代码 | 级别 |
| --- | --- | --- |
| 禁用词与套话 | `banned-phrase` | error |
| 翻译腔/空泛句式 | `ai-phrase` | warning |
| 标题没有判断 | `title-no-verdict` | warning |
| 标题像话题或过短 | `title-topic` | warning |
| 标题过长（>16 汉字） | `title-too-long` | warning |
| 口语/工程俚语（掉点、补不回） | `colloquial` | warning |
| 单句过长（>60 汉字） | `sentence-too-long` | warning |
| 单页要点超过 5 条 / 单条超过 40 字 | `too-many-bullets` / `bullet-too-long` | warning |
| 口播超过 120 字 | `notes-too-long` | warning |
| 报告图片链接缺失 | `ART-IMG-MISSING` | error |
| 图片没有 alt / 图片后没有图注 | `ART-IMG-ALT` / `ART-IMG-CAPTION` | warning |
| 图片没被任何报告引用 | `ART-IMG-ORPHAN` | warning |
| 图号不连续 | `ART-FIG-NUM` | warning |

机械检查只抓高置信度问题；标题有没有洞察、目标与实验是否对应，仍要人读。
**图内文字**（坐标轴、图例、图内标题）在 PNG 里，机械检查读不到，仍按人工/OCR 处理；
`text_check.py` 覆盖页片/报告文字，`text_consistency.py --exports` 覆盖报告里的图片块
（链接、alt、图注、图号、孤立图），两者不重叠。

## 人工检查清单

交付前逐条打勾：

- [ ] 标题序列连读成故事，不重复、不跳步；
- [ ] 每页只有一个主张，标题就是结论；
- [ ] 研究内容与创新点分开，各自回答不同问题；
- [ ] 每个目标都有实验，定性与定量都写；
- [ ] 每个数值能指到实验、公式或任务书；
- [ ] 指标名、口径、条件、考核方式四处一致；
- [ ] 结论写了达到与未达到，没有掩盖失败；
- [ ] 图片链接存在、alt/图注齐全、图号连续、`figures/` 无孤立图（`--exports` 机械查）；
- [ ] 图注、表注、正文的术语和单位一致；
- [ ] README 类文字走 development，不在本 skill 重写。

## 用户交互文字（弹窗 / 界面 / 状态栏）

产品面向用户的文字（通知、状态栏、弹窗、报错、设置项说明）**只写两类**：

1. **当前状态** —— 让用户知道现在处于哪一步（`已推送 12:31 · 对方一致`、`导出中 12/40`）；
2. **要求用户操作** —— 需要他做决定或动手（确认框、`完整副本要手动拷`、`起点对不上，请对方重导`）。

其余一律不播报：同步完成、自动收包、自动留包、拉下来几个包这些例行结果进状态栏一句、
悬停详情、更新记录或日志。**判断标准是"用户需不需要知道 / 需不需要动手"，不是"这件事发生了没有"**。
频繁的成功提示会把真正的异常淹掉，用户会直接说"怎么一直在弹"。

写法：

- 一条通知只说一件事，能进状态栏的就不弹窗；报数一行一项，不在括号里塞理由；
- 设置项是一行名字 + 一句话说明；长解释进制 README / 帮助窗口；
- 例外的"必须弹"只有：出错、需要用户决定、**动到用户已有数据**（删除、覆盖、回滚、恢复）。

怎么测：在项目测试里断言"该静默的时候没有提示"（例如自动收包只往状态栏写一句、
后台同步不写状态栏、自动留包成功不弹通知），同时保留"该弹的时候弹了"的正向用例。
只测正向会把降噪改回去都没人发现。
