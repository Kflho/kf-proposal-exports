# 页片与报告的文字规范

> 这份文件管「说什么、怎么说」：页片的标题、要点、口播、图注，申报书与技术方案的段落，
> 实验报告的结构。图和版式在 `SKILL.md` 与 `ppt-deck.md`；机械检查用 `scripts/text_check.py`。
> 仓库 README、用法文档、代码注释不在本文件范围，按 `kf-personal-development` 的 `readme.md`。

## 逻辑骨架

申报书、技术方案、汇报页片共用一条逻辑链，缺一环就补，不靠辞藻填空：

```text
背景 → 现状（别人怎么做、卡在哪）→ 问题（一句可验证）
     → 研究内容（做什么，与研究目标对应）
     → 创新点（和现有做法的差异）
     → 目标（从研究内容分解，可量化）
     → 技术路线（怎么做）
     → 实验（每个目标至少一个实验，先定性后定量）
     → 结论（达到什么、没达到什么、下一步）
```

四条边界：

- **研究内容 ≠ 创新点**：研究内容回答「做什么」，创新点回答「和别人的差别在哪」。两节不能互相改写。
- **目标来自研究内容**：目标编号与任务书对应，不另起一套。
- **每个目标都有实验**：没有实验的目标不写进目标页；写不出的实验说明目标不可验证。
- **数值有出处**：来自实验、公式或任务书；没有出处就标待定，不猜。

## 页片逻辑

1. **先写标题序列**：把每页标题抄成一份清单，只读标题能讲完整个故事。读不通就改标题，
   不靠正文补。
2. **一页一个主张**：答案放标题，证据放正文（图、表、公式），口播解释「为什么」。
3. **标题写结论**：带判断或数字。话题式标题改写成结论式，例：

   | 话题式 | 结论式 |
   | --- | --- |
   | 模型 | C-W 方程开环临界稳定，必须反馈 |
   | 能控性分析 | 只开径向发动机时秩为 3，切向漂移拉不回来 |
   | 结果对比 | 同一组极点下，解耦解把切向推力从 20 降到 1.8 |

4. **目标页与实验页一一对应**：给一张对照表，左列目标编号，右列实验、指标、结论。评审能顺着
   表格找到证据。

## 分体裁规范

### 页片

| 部分 | 写法 | 反例 | 检查 |
| --- | --- | --- | --- |
| 标题 | 一句结论；**≤16 汉字、一行**（超了拆页）；主动语态；带数字 | 「模型」「结果对比」这类话题；20 字以上的整句 | `title-no-verdict`、`title-topic`、`title-too-long` |
| 语体 | 学术表述：可用率下降 / 测距中断 / 仅增加站数无法恢复 | 「掉点」「补不回」「拉满」这类工程口语 | `colloquial` |
| 要点 | 3–5 条；每条一句话、≤40 字；「**粗体引导词**：一句说明」 | 整段论文体；一页塞 8 条 | `too-many-bullets`、`bullet-too-long` |
| 口播 | ≤120 字；能直接念；结论 → 证据 → 所以；不照读页面 | 把页面文字念一遍 | `notes-too-long`，其余人工 |
| 图注 | 指标名 + 口径 + 单位；与图内文字逐字一致 | 只写「如图所示」 | 人工 |
| 表头表注 | 单位进表头；条件进表注；数字对齐 | 单位散在单元格里 | 人工 |

### 申报书与技术方案

| 段落 | 写法 | 反例 |
| --- | --- | --- |
| 背景 | 说清为什么现在做：现状变化、约束、代价 | 从宏大叙事开头，落不到本项目 |
| 研究现状 | 别人做到哪、卡在哪、与本项目的关系 | 罗列文献，不给判断 |
| 问题 | 一句可验证的问题，能对应后面的目标或实验 | 口号式问题，无法验证 |
| 研究内容 | 做什么；与目标、任务书对应 | 把创新点写成研究内容 |
| 创新点 | 与现有做法的差异，给对比维度 | 只说「首次提出」，没有对比 |
| 目标 | 从研究内容分解；可量化；编号对应任务书 | 目标写成愿望 |
| 技术路线 | 每一步怎么做、依据是什么 | 只画流程图，不写依据 |
| 指标 | 指标名、口径、条件、考核方式四件事写全 | 只给数值，不写条件 |
| 实验设计 | 每个目标至少一个实验；先定性后定量 | 实验与目标对不上 |
| 结论与预期成果 | 达到什么、没达到什么、下一步 | 只写成绩，不写限制 |

### 实验报告

按 GB/T 7713.3 的骨架组织，正文至少包含：

- 目的：验证哪个目标；
- 方法：数据、参数、对照；
- 结果：数值与图，标明口径；
- 讨论：与预期或论文的差异，失败原因；
- 结论：达到与未达到，下一步。

### 说明类

- 变更说明、汇报消息：一句结论开头，说清改了什么、影响谁、下一步；
- README、用法文档：不在本文件，按 `kf-personal-development` 的 `readme.md`。

## 去 AI 味

词表和模式在 `assets/text/banned.json`，不在正文逐字列举。规范只描述类别：
起跑式铺垫、意义拔高、宣传语、客服腔、套话收尾、假对比、三段套话、模糊权威、翻译腔。

下面是真实技术句的改法，重点是把「评价」换成「条件 + 数值 + 结论」：

| 空泛写法 | 规范写法 |
| --- | --- |
| 对系统鲁棒性的提升效果较为明显 | 参数摄动 20% 时，跟踪误差从 0.8 m 降到 0.2 m |
| 该方法在工程应用中具备较好的参考价值 | 8 站、100 ms 时延下仍收敛，可直接接现有控制器 |
| 结果验证了方案的有效性与可行性 | 三种工况均未失稳，最大超调 4.2% |
| 从整体上看，方案兼顾了性能与成本 | 同样跟踪精度下，求解时间从 12 ms 降到 5 ms |
| 该问题受到了广泛关注 | 2024 年后有三类做法：集中式、分布式、事件触发；前两类在 8 站以上失稳 |

改完回读：有没有新增信息，条件、范围、否定、归因是否还在。

## 可读性（读者没有开发背景）

前面几节（术语、严肃性、句子、一致性）都在为同一件事服务：**一个没参与开发、不知道脚本长什么样的人，
读到这句话能不能懂**。这一节把它写成可检查的判据。

读者模型：第一次用这个产品的人、换台机器接手的 agent、半年后回来改代码的自己。他们**没有**：
窗口截图、上次对话、代码里的对象名、内部流程。所以每条文字都要能**单独拿出来读**。

| 规则 | 不许出现 | 例子（反 → 正） |
| --- | --- | --- |
| R1 指代不靠上下文 | 句子以「这个 / 那个 / 它 / 该 / 此 / 上面 / 刚才」开头 | 「它还没上报」→「另一台电脑还没上报状态」 |
| R2 不用方位词指界面 | 顶部 / 上方 / 这一行 / 记录里 / 那个窗口 | 「记录顶部写着编号」→「同步包的更新记录窗口第一行显示本机当前的状态编号」 |
| R3 引号里的口语不当名字 | 「我现在」「这边」「那条」当名词 | 「记录写着「我现在」的编号」→「记录写的是本机当前的状态编号」 |
| R4 不堆名词化短语 | 写着…的编号 / 显示…的状态 | 「顶部写着本机的状态编号」→「第一行显示本机当前的状态编号」 |
| R5 不用自造缩写与口语 | 留包 / 重导 / 推拉 / 收包 / 货架 / 指纹 / 落点 / 收口 / 捞回来 / 拷 / 弄 | 「重导一份」→「重新导出一份」；「能捞回来」→「可从回收目录恢复」 |
| R6 内部术语第一次出现给白话 | 状态编号 / 基准 / 世代 / 完整副本 / 更新包 | 「基准对不上」→「这份更新包的起点与本机的完整副本不是同一份」 |
| R7 不用比喻动词（开发文字） | 守 / 兜底 / 挂在 / 长在 / 吃进 / 塞进 / 落进 / 扛 / 拽 / 崩了 / 炸了 | 「测试守着它」→「由这条测试验证」；「塞进 notes」→「放进 notes」 |
| R8 不压缩成对仗短语 | 「在测什么、守在哪」「是什么、为什么、怎么办」 | 拆成两句完整的话：验证什么行为、哪一处出错会让它失败 |
| R9 不用前文指代开头 | 这里 / 上面 / 这条 / 那句 / 该 / 此 | 写出具体对象，每条单独能读 |
| R12 不用没有名词的指代 | 这一段 / 那一条 / 那一份 / 这个 / 那个 | 「只排版刚粘贴的那一段」→「只排版这一次粘贴的内容」 |
| R13 不用压缩句（只有对象和否定） | 原图不留 / 正文不动 / 消息不拆 | 补上谁做：原图会被删除 / 正文保持不变 / 带图的消息不加 |
| R14 用了术语表里的禁用别名 | 完整副本 / 货架 / 留包 / 第 N 代 | 用术语表的唯一叫法：完整备份 / 远程仓库 / 导出 / 第 N 版 |
| R16 不写本机绝对路径与只有作者才有的上下文 | `D:\data\...`、`C:\Users\...`、`/home/...`、`~/...`、`\\主机名\共享` | 写仓库内相对路径（`bin/reference_docs/references/`）；必须指外部位置时写机构与文件名（「商务部《对外投资合作发展报告》」）。同一句里的本机目录、上次会话、窗口截图都属于读者没有的上下文，一并删掉 |
| R17 交付文档不写仓库路径 | `bin/reference_docs/references/`、`data/ocr/`、`src/ocr_pages.py` | 写文件名、来源或持有人（「《可引用的材料》第二节」「条款摘录表由成员 C 保管」）。交付文档的读者手里只有这一份文件，按路径找不到东西。README、AGENTS、CLAUDE 与脚本注释例外，它们的职责就是讲目录 |

两条人工读法（机械检查替代不了）：

1. **单独成句**：把每条界面文字、每个测试用例名、每个文档标题抄到一张清单里，**打乱顺序**逐条读。
   读到需要回头找上文、或者脑子里要补一个主语，就是不合格；
2. **换人读**：找个没碰过这个项目的人读一遍，让他复述"这条在说什么"。复述不出来就是不合格。

### 抽查（每批都做，不能只看脚本 0 error）

1. 每批抽 20–30 条：**设置说明优先**，其次是通知、弹窗、菜单、状态栏；
2. 打乱顺序逐条问四件事：**谁对什么做什么**？指代有没有名词？是不是压缩句（「原图不留」）？
   只看这一条，知不知道会发生什么、要不要动手？
3. 记录文件:行、原句、问题、改法。能补成完整句的补；标题已经讲清楚的，直接把说明删掉；
4. `readability_check.py --root <项目> --dump` 导出清单（`文件:行<TAB>文字`），
   抽完一批再抽下一批，直到覆盖全部界面文字。

机械部分：`readability_check.py`（R1–R14、R16；R14 读项目 `术语表.md` 的「禁用别名」列，
英文别名与单字跳过；R16 报绝对路径与家目录写法；`--docs` 同时扫 Markdown 正文，README 也算开发文档）
与 `text_consistency.py`（去 AI 味；默认只打印 error，`--warnings` 看 warning；
`node_modules` 与历史文档默认跳过）。`--dump` 导出全部界面文字，供人工抽查。
破折号（B8）不进机械检查：技术文档里成对破折号多半是正常解释，留给人读；
层叠「的」（F26）只查同一分句内、不含引号/运算符/表格的写法。

```bash
python scripts/readability_check.py --root <项目> [--tests <测试仓>] [--json]
```

它扫三类文字：界面字符串（Notice / 设置项 / 弹窗 / 命令名）、测试用例名（`check('…')` 的第一个参数）、
Markdown 标题；按 R1–R9 报「依赖上下文 / 方位词 / 口语标签 / 名词堆叠 / 自造缩写 / 术语未解释 /
比喻动词 / 压缩对仗 / 开头指代」，按 R16 报本机绝对路径与家目录写法。加 `--comments` 再扫 `.ts` 注释（R7–R9，只报 warning）。
项目根可放 `readability.json`：`{"allow": ["留包"], "glossary": "bin/reference_docs/术语表.md"}`，
登记过的词与术语不再报。**改完必须人工按上面两条读法再过一遍**：脚本只能证明"没有明显依赖"，
证明不了"读得懂"。

## 语言风格与情景匹配（默认为论文 / 报告语体）

先定情景，再定语体。**没有特别说明时，一律用论文 / 报告的正式书面语**；不因作者习惯降级为口语。
口语只允许出现在口播稿、对话示例这类明确要"说给人听"的地方。

| 情景 | 语体 | 例子 |
| --- | --- | --- |
| 论文 / 报告 / 申报书 / 技术方案 / 答辩材料 | **正式书面语（默认）** | 「将仓库打包为单个文件」不是「把仓库打成包」 |
| PPT 页片 | 结论式书面语，短句，一页一个结论 | 标题写结论，不写话题 |
| 口播稿 | 口语，但要说清楚 | 可以「我们先看…」，不能含糊 |
| README / 帮助 | 面向用户的规范书面语，说明操作与结果 | 「传输」不是「搬来搬去」；「丢失」不是「弄丢」 |
| 用户交互（通知 / 设置 / 报错） | 简短明确，一句状态或一句操作 | 仍禁口语、黑话、比喻 |
| 开发文档 / 注释 | 规范技术书面语 | 见「开发文字」一节 |
| 项目笔记 / 工作笔记（Obsidian） | **按操作组织的结论式清单**：一条一个用户能做的操作，每条单独能读 | 「导出：完整副本为整库快照」不是「两种包：快照与差量」（后者是概念分类，不是功能）；不写实现细节与比喻 |

### 严肃性检查（正式内容）

面向用户 / kf 的正式文字用书面语。humanizer 管"AI 腔泡沫"，这一节管**语体**：同一件事，
书面材料里能不能这样写。范围：状态栏、通知、设置项、弹窗、命令名、报错、README、帮助、开发文档、
报告与申报书。

| 类别 | 不严肃的写法 | 严肃写法 |
| --- | --- | --- |
| 口语动词 / 缩写 | 走 git、拷过去、捞回来、搬来搬去、打成包、粘（单字） | 通过 Git 传输、复制、从回收目录恢复、传输、打包为、粘贴 |
| 叠词 / 口头量词 | 一张一张、一个一个、一遍一遍、一点点 | 逐张、逐个、逐次、写明确的数量或程度 |
| 网络流行语 / 情绪词 | 搞定、翻车、坑、这玩意儿、说白了、离谱、真香 | 完成、失败、问题、该功能、即、异常 |
| 比喻 / 拟人 | 站在那份完整副本上、停在旧那份上、货架、回礼、收口、白跑一趟 | 以那份完整副本为基准、仍使用旧完整副本、远程仓库、回传、整理、无需变更 |
| 开发者黑话 | 指纹、镜像策略、引擎、收件箱、`full` 与 `changes`、`stateId`、`hash` | 基准编号、按对方状态覆盖、程序、收包目录、完整副本与更新包、内部编号 |
| 省略 / 电报体 | 编号还差一点、没变化、已推拉、还没跑完 | 两边内容尚未完全一致、没有变更、已完成推送与拉取、尚未完成 |
| 语气与程度 | 其实、挺、蛮、一下子、吧、呢、就好 | 删掉；需要强调时给条件与数值 |
| 营销腔 | 一键、无缝、彻底、完美、领先 | 具体动作与条件（「点击一次完成…」「X 条件下下降 N%」） |

**口语化 / 黑话逐句检查**：正式文档（论文、报告、申报书、README、技术方案）逐句读一遍，
出现上表任一类就改；口播稿与对话示例除外。README 与界面文字尤其不能出现"搬、弄、搞、坑、翻车"。

判据：

- 同一概念先按项目术语表选词（一条概念只留一种叫法，别名进禁用表），再按本表调语体；
- **界面文字优先**：一次用户动作最多一条通知；设置项一行名字 + 一句话说明；报错给原因和下一步；
- 文档同样适用：README、帮助窗口、开发文档、agent 文档。**历史记录类文档**（实施计划、复盘）
  可以保留当时的原话，但现行规范、以及被这些文档引用的结论必须同步；
- 引用用户原话、代码标识符、Git 命令不算口语；
- 改写后回读：条件、范围、否定、下一步有没有丢；有没有把「可能」写成「确定」。

## 语言风格检查（标题、文件名与正文通用）

适用范围：任务书、大纲、说明、报告、方案与过程材料的标题、文件名、小节标题和正文。
本节的判据落在 `data note` 的「语言风格规范」与 `project note` 的「单一功能」「单一对象」上。

### 写作前（先做完这三步，不写完再改）

1. 定读者与功能：这份文件给谁看、只承担哪一项功能。两项功能就拆成两份文件；
2. 定骨架：先列出文件名、一级标题、小节标题，每条单独抄出来能读懂；名词用常见词，写全，不用简称；
3. 定句式：一句话讲一件事，主语、谓语、宾语齐全，先说对象再说动作，不用否定式压缩句。

动手时以下五类不写。这类写法不影响事实，却让人以为在凑字数。

| 不写 | 改为 | 原因 |
| --- | --- | --- |
| 「三件事」「两点说明」「以下几方面」这类数字预告 | 直接写内容；确需计数时写「以下三项」并紧跟条目 | 预告替代了内容 |
| 「不合写」「不互相等稿」「缺什么当天提出」 | 「每名成员独立完成所负责章节，不与他人合写」「缺少的材料在当日提出」 | 压缩否定句缺主语 |
| 对仗与排比：「先…再…最后…」「既…又…」 | 按实际顺序写完整句 | 修辞替代了信息 |
| 成对破折号插入解释 | 拆成两句 | 打断句子 |
| 「显著」「极为重要」「充分发挥」这类评价词 | 写出条件、数值、可核对的事实 | 没有信息量 |

本节的机械部分抓不到上面这些，只能人工过；改完回读一遍，确认条件、范围、否定没有丢。

| 判据 | 不合格 | 合格 |
| --- | --- | --- |
| 标题与文件名用常见词，写完整 | 撰写口径、页计划、要交什么、任务怎么分 | 调研报告大纲、汇报演示文稿大纲、交付成果、工作任务分解 |
| 句子成分完整，不用压缩祈使句 | 别混文本；拿不到就写；压成一段话 | 引用时须区分文本来源；无法获取时写明"未获取到"；压缩为一段说明 |
| 不用行话与内部简称 | 口径、台账、落点、红线、跑通、堵点、份一、2.1 | 统计范围与计量方式、材料清单、调研对象、引用限制、已见成效、受限环节、任务一、调研内容第二节 |
| 不自造搭配与比喻 | 给料、揉成一条、塞进、硬拼、拍板 | 分发材料、合并为一条论证、写入、强行套用、确定 |
| 文件开头写明用途与读者 | 直接从条目开始 | 第一段写"本文件规定……，谁使用；其余内容见《××》" |

人工读法三条：

1. 把标题、文件名、小节名抄成清单，打乱顺序逐条读。读不出"这是什么、给谁看"的，改写；
2. 正文逐句对照上表，重点查祈使句与省略句。改完回读，确认条件、范围、否定没有丢；
3. 每句问一次"这句是给谁看的、为什么在这份文件里"。答不出的删掉，或移到对应文件。

失败案例：一份小组任务书的文件名写成「撰写口径_报告.md」「页计划_汇报.md」，小节写成「要交什么」「任务怎么分」「还没确定的事」，正文夹着"按份给料，谁用谁查""拿不到就写"。读者是第一次看这份材料的组员，判断不了每份文件管什么，全部返工。文件名和小节名承担导航作用，写不清等于没写。

本节管句子与命名；注释、用例名、日志的写法见「开发文字」，文件职责的划分见「文档按功能拆分」，三节不重叠。

## 开发文字（注释 / 用例名 / 日志 / 文档）

写给下一个改代码的人看。判据：**没有上下文也能读懂，说清对象和动作**。

- 写"谁、做了什么、结果是什么、怎么验证"，不写比喻动词：守 / 兜底 / 挂在 / 长在 / 吃进 / 塞进 /
  落进 / 扛 / 拽 / 崩了 / 炸了；
  例：`test/bundle.test.ts 守着它` → `由 test/bundle.test.ts 验证`；`塞进 notes` → `放进 notes`。
- **用所在领域现成的说法**（正面规则：不是在脑子里找同义词，是去查这个领域怎么写）：
  动作和搭配先看该领域已有的文字 —— 官方文档、同领域项目的 README、项目术语表；
  能用通用词（导出 / 应用 / 移动 / 覆盖 / 写入 / 恢复）就不自创，也不借别的领域的比喻。
  例：`把仓库搬到另一台机器` → `导出为包，在另一台机器上应用`；`把配置塞给插件` → `把配置写入插件设置`；
  `让包落进仓库` → `把包应用到仓库`。查不到现成说法时，按"动作 + 对象"直说，并在项目术语表登记。
- 不压缩成对仗短语：`在测什么、守在哪` → `验证的是什么行为、哪一处出错会让它失败`。
- 不指代前文：这里 / 上面 / 这条 / 那句 / 该 / 此；每句单独拿出来能读。
- 说明句写清"谁对什么做什么"：不用「原图不留」「正文不动」这种压缩句，也不用没有名词的
  指示代词（「那一段」）；例：「只排版刚粘贴的那一段」→「只排版这一次粘贴的内容」。
- 用例名写「操作或输入 → 期望结果」，不写"守着…"；失败信息写清"哪里不对、期望是什么"。
- 注释写：为什么这样做、约束是什么、改回去会怎样；不写段子、吐槽、口令式短句。
- 日志写：时间、动作、结果、数量；不写评价。
- 例外：`裸仓库`（Git 术语）、引用用户原话时保留原话并标出处。
- **项目专用词只记在该项目的术语表里**，不要写进本 skill；换项目时以项目术语表为准。
- 检查：`readability_check.py --root <项目> --comments --tests <测试仓>`（R7–R9）。

## 去除重复

一个信息只写一处，其他地方引用（完整引用或写明"引用 xx 相关部分"）。

| 位置 | 不重复什么 | 写法 |
| --- | --- | --- |
| 标题 / 小节 | 标题已经说清楚的，不再起一段复述 | 标题直接给结论；正文补证据、条件、例外 |
| 设置项 | 名字能讲清楚就不写说明；要写就写用户关心的，不复述名字 | 例子：`显示用户名` 不写说明；`默认宽度` 写「留空则不加尺寸」 |
| 通知 / 弹窗 / 状态栏 / 日志 | 同一事实只出现在该出现的那一层 | 例行结果进状态栏与日志；需要用户动手才弹通知 |
| README / 帮助 / AGENTS / 笔记 | 同一结论只有一个权威位置 | 其他位置写一句链接或"见 xx" |

自检：

- 把标题和它下面第一段并排看，说的是不是同一件事；是就删段落、或把段落改成证据；
- 设置项去掉标点后，说明里是否包含名字；包含说明这条说明没写新东西；
- 同一份材料里搜一个结论的关键词，出现两次以上就要合并到一处、其余改成引用。

机械检查：`readability_check.py` 的 R10（标题与首段重复）、R11（设置说明复述名字）。

## 文档按功能拆分（内容规范）

一个文件只服务一类读者；放错的内容不是"多写一点"，是让人读不下去。

**内容该放哪个文件**（README / 项目笔记 / AGENTS / dev / changelog / 报告 / skill references、
项目笔记内部各节放什么）按 `kf-personal-service` 的 `references/writing.md` 执行，本文件不重复。

### 开发文档与产物、产物与产物严格分离

**绝对不能混着写。** 开发文档是给接手的人看，产物是给评审 / 听众 / 用户看；它们是两组文件。

- **开发文档 ≠ 产物**：AGENTS / CLAUDE / `references/` / `dev/` 里写实现、约束、测试；
  申报书、报告、PPT、README 只写交付内容。开发记录不写进交付物，交付文字也不塞进开发文档；
- **产物之间不搬运**：申报书 / 报告（正文）、PPT 页片（标题 + 要点）、口播稿（讲稿）、
  配图说明（图注）各自成文：
  - PPT 口播稿不写进报告；
  - 报告章节不写进页片备注；
  - 配图说明不混进正文论证；
  - 同一段文字只有一个主文件，其他产物引用（「见报告 3.2」），不复制。
- 检查：打开一个文件，问「这句话是给谁看的、为什么在这个文件里」；
  A 文件里出现 B 角色的词（本页 / 口播 / 幻灯片 / 备注 / 报告第 X 节 / 申报书正文）就是混了。

检查：`readability_check.py --docs` 会额外扫 Markdown 正文，README 里出现
`Internal:`、`test/…`、日期、`用户报/实测/踩坑` 会报 R15。

## 文字工作交付清单（逐条报状态）

文字类任务和其他开发一样，**按条目交付，不按"我改了什么"交付**。清单落盘，未勾选项写原因。

| 条目 | 判据 | 证据 |
| --- | --- | --- |
| 术语唯一 | 项目术语表；同一概念只有一种叫法 | 扫描脚本 0 违规 |
| 标题与文件名可读 | 打乱顺序逐条读，能答出"这是什么、给谁看" | 人工过清单 |
| 语言风格匹配 | 默认论文 / 报告书面语；口语只出现在口播稿 / 对话示例 | 逐句读，口语与黑话 0 处 |
| 句子完整 | 能回答「发生了什么、要不要我动手」；无无主语句 | 逐条人工过 |
| 只写状态与操作 | 通知不含实现理由、内部路径、过程描述 | 逐条人工过 |
| 播报频率 | 一次用户动作 ≤1 条通知（需要用户决定的例外单列） | 场景走查 + 测试 |
| 设置项 | 一行名字 + 一句话说明；不复述名字；≤1 句 | 字段表逐条看 |
| 标点与格式 | 项目级规则（句末句号、引号、中英空格、量词） | 扫描脚本输出 |
| 覆盖范围 | 界面 / README / 帮助 / 开发文档 / agent 文档 / 笔记 / 清单，逐类点名 | 清单勾选 |
| 内容分离 | 开发文档 / 产物 / 不同产物之间不互相搬运 | 每类文件抽查首段，无角色词串台 |
| 一致性 | 代码、文档、帮助、笔记同一说法 | 交叉检索 0 冲突 |
| 机械守卫 | 规则有脚本、有测试，并进收尾闸门 | 脚本与用例 |

术语表本身也是交付物：概念 / 唯一叫法 / 禁用别名 / 例外（引用原话、代码字段），跟着项目走。

## 用户交互文字（弹窗 / 界面 / 状态栏）

产品面向用户的文字（通知、状态栏、弹窗、报错、设置项说明）**只写两类**：

1. **当前状态** —— 让用户知道现在处于哪一步（`已推送 12:31 · 对方一致`、`导出中 12/40`）；
2. **要求用户操作** —— 需要他做决定或动手（确认框、`完整副本要手动拷`、`起点对不上，请对方重导`）。

其余一律不播报：同步完成、自动收包、自动留包、拉下来几个包这些例行结果进状态栏一句、
悬停详情、更新记录或日志。**判断标准是"用户需不需要知道 / 需不需要动手"，不是"这件事发生了没有"**。
频繁的成功提示会把真正的异常淹掉，用户会直接说"怎么一直在弹"。

写法：

- 一条通知只说一件事，能进状态栏的就不弹窗；报数一行一项，不在括号里塞理由；
- 设置项是一行名字 + 一句话说明；功能说明先写"做什么"，再写限制；实现理由与示例留在 README / 帮助窗口；
- **不写实现**：流水线顺序、模块名、并发、缓存、幂等这些词用户用不上；用户只关心"打开之后会发生什么、
  什么时候不生效"。例：页面说明 `按排版流水线顺序列出开关` → 改成"控制笔记里的缩进、标题、聊天记录、公式与空格"；
  设置项 `避免并发撞名丢图` → `一次粘多张时一张一张保存，文件名不会重复`；
- 页面说明一句话、不超过 30 字，列用户会看到的内容；不写顺序、分组理由、模块名；
- **名字用用户动作**：`接管`、`挂载`、`注册`、`引擎`、`流水线` 这类是实现词，用户看不懂；
  写用户会做什么、会看到什么（`接管图片粘贴` → `粘贴图片时逐张保存`）；
- 同一页、同一个菜单里同一概念用同一个词（`内容板块` / `内容块` 不混用）；命令名统一动词开头、
  同类操作同一句式（`转换整个仓库的图片格式`，不写 `把…转换为…`）；
- 例外的"必须弹"只有：出错、需要用户决定、**动到用户已有数据**（删除、覆盖、回滚、恢复）。

怎么测：在项目测试里断言"该静默的时候没有提示"（例如自动收包只往状态栏写一句、
后台同步不写状态栏、自动留包成功不弹通知），同时保留"该弹的时候弹了"的正向用例。
只测正向会把降噪改回去都没人发现。
