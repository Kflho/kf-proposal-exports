# 写作规范调研（R1）

> 目的：给 `references/text-quality.md` 提供可追溯的规则来源，回答「哪些体裁要管、判据是什么、
> 哪些能机检」。每条规则都要能回到一张证据卡。

## 问题卡

- **要解决什么**：页片和申报材料的文字空、逻辑散；需要一份分体裁的写法与判据。
- **现状**：`text-quality.md` 只有标题、长度、禁用词三类，缺逻辑层和体裁层。
- **约束**：与用户 project note 的逻辑链一致；只覆盖本项目实际交付的文种；规范要能被
  `text_check.py` 部分机械检查。
- **完成判据**：给出体裁清单、每类判据、规则到来源的映射，并说明哪些只能项目内约定。
- **停止条件**：能回答 ①权威规范覆盖哪些体裁 ②哪些只能项目内约定 ③哪些可机械化。

## 证据卡

### E1 页片 action title

- **来源**：[Slideworks: How to Write Slide Action Titles Like McKinsey](https://slideworks.io/resources/how-to-write-action-titles-like-mckinsey)，2026-10-21 读取。
- **主张**：标题写这一页的结论，不写话题；不超过 15 个词、最多两行；用主动语态；具体、带数字；
  先写标题序列再写页，只读标题要能讲完整个故事（SCQA、问题—方案—证据）。
- **条件**：咨询/商业汇报的页片；技术汇报可借用结构，长度按中文习惯折算。
- **本机验证**：读过全文与示例；「标题写结论」与「先标题后页」两条可直接用。
- **结论**：可用，作为页片标题与标题序列的一手依据。

### E2 科技报告结构

- **来源**：[GB/T 7713.3-2014 科学技术报告编写规则](https://www.nstrs.cn/standard/detail?arid=4587)，2026-10-21 读取标准说明页。
- **主张**：科技报告由前置（封面、题名页、辑要页、前言、摘要、目次、图表清单、符号说明）、
  主体（引言、正文、结论、建议、参考文献）、结尾（附录、索引、封底）三部分组成。
- **条件**：科技报告体裁，不是申报书；只取结构，不套排版格式。
- **本机验证**：读的是标准说明页，不是标准全文；结构要素可用，细则未逐条核。
- **结论**：可用，约束实验报告和结题报告的骨架；不拿它规定申报书章节。

### E3 金字塔原理

- **来源**：[think-cell 中文说明](https://www.thinkcell.com/zh/blog/using-the-pyramid-principle-to-build-better-powerpoint-presentations)，2026-10-21 读取（页面正文被截断，只取通用原则）。
- **主张**：结论先行、以上统下、归类分组、逻辑递进。
- **条件**：通用表达原则，不提供具体字数或句式。
- **本机验证**：只核到页面标题与公开摘要，属于二手依据。
- **结论**：可作逻辑原则，不作机械规则。

### E4 用户 project note（本项目权威）

- **来源**：用户 project note，登记在 `kf-personal-service` 的 `notes` 里（路径不进仓库）。
- **主张**：流程是「解读参考资料 → 写项目笔记 → 论文撰写 → 仿真实验」；内容分研究现状、
  研究内容、目标、实验；创新点与研究内容要分开；目标来自研究内容分解；每个目标对应实验，
  先定性再定量；实验必须自己读懂论文、逐公式搞懂再写脚本。
- **条件**：用户自己的项目约定，优先级高于外部通用规范。
- **本机验证**：原文读过；本 skill 的项目 note 模板与之一致。
- **结论**：本项目最高依据；与外部规范冲突时以它为准。

### E5 kf-personal-development 的写作规则

- **来源**：`kf-personal-development/references/readme.md`、`appendix/latex.md`、`text-review.md`。
- **主张**：README 只做入口、快速开始能照抄；latex 写作要求数值来自实际运行、不美化、
  框架确认后再写正文；去 AI 味按 humanizer-zh 规则。
- **条件**：仓库文档与论文写作；README 归 development，不在本 skill 重复。
- **本机验证**：本会话读过原文。
- **结论**：可验证性、不美化两条进入本规范；README 结构整段委托给 development。

### E6 去 AI 味模式

- **来源**：`kf-personal-development/references/text-review.md`（humanizer-zh 归一口径）。
- **主张**：起跑式铺垫、AI 高频词、意义拔高、宣传语、客服腔、套话收尾、假对比、三段式、
  模糊权威、破折号与层叠「的」。
- **条件**：通用文风；机械检查只覆盖高置信度子集。
- **本机验证**：`text_review.py` 的实现与规则一致。
- **结论**：词表与模式放 `assets/text/banned.json`，规范只描述类别，不逐字列举。

## 体裁清单与判据

| 体裁 / 段落 | 合格判据 | 来源 | 机检 |
| --- | --- | --- | --- |
| 页片标题 | 写结论不写话题；≤30 汉字、最多两行；主动语态；带判断或数字 | E1、E4 | `title-no-verdict`、`title-too-long`、`title-topic` |
| 页片标题序列 | 只读标题能讲完故事；页与页不重复、不跳步 | E1 | 人工 |
| 页片要点 | 一页一个主张；3–5 条；每条一句话、≤40 字；先结论后证据 | E1、E3 | `too-many-bullets`、`bullet-too-long` |
| 口播 notes | ≤120 字；口语；结论 → 证据 → 所以；不照读页面 | E1、E4 | `notes-too-long`，其余人工 |
| 图注 / 表头 / 表注 | 与图内文字、正文指标逐字一致；写口径与单位 | `text-norms.md`、`indicator-wording.md` | 人工 |
| 申报书：背景 | 说清为什么现在做：现状变化、约束、代价 | E4 | 人工 |
| 申报书：研究现状 | 别人做到哪、卡在哪、和本项目的关系；不以罗列代替判断 | E4 | 人工 |
| 申报书：问题 | 一句可验证的问题；能对应到后面的目标或实验 | E4 | 人工 |
| 申报书：研究内容 | 做什么；与研究目标、任务书对应；**与创新点分开写** | E4 | 人工 |
| 申报书：创新点 | 与现有做法的差异，给对比维度；不把研究内容改写成创新点 | E4 | 人工 |
| 申报书：目标 | 从研究内容分解；可量化；编号与任务书对应 | E4 | 人工 |
| 申报书：技术路线 | 怎么做；每一步有依据；不写没验证的承诺 | E4、E5 | 人工 |
| 申报书：指标 | 指标名、口径、条件、考核方式四件事写全 | `indicator-wording.md` | 人工 |
| 申报书：实验设计 | 每个目标至少一个实验；先定性后定量 | E4 | 人工 |
| 申报书：结论 / 预期成果 | 达到什么、没达到什么、下一步；数值来自实测 | E4、E5 | 人工 |
| 实验报告 | 目的、方法、结果、讨论、结论齐全；结构可借 GB/T 7713.3 | E2、E5 | 人工 |
| 说明类：README | 不在本 skill；按 `kf-personal-development` 的 `readme.md` | E5 | 委托 |
| 说明类：变更说明 / 汇报消息 | 一句结论开头；说清改了什么、影响谁、下一步 | E3 | 人工 |

## 规则 → 来源 → 判据 → 机检

| 规则 | 来源 | 判据 | 机检 |
| --- | --- | --- | --- |
| 标题写结论，不写话题 | E1、E4 | 标题里有判断词或具体数字；只读标题知道结论 | `title-no-verdict`、`title-topic` |
| 标题长度 ≤30 汉字、最多两行 | E1（15 词折算） | 超过即拆页或改短 | `title-too-long` |
| 标题序列成故事 | E1 | 抄出全部标题连读，通顺、不重复、不跳步 | 人工 |
| 一页一个主张 | E1、E3 | 一页只回答一个问题 | `too-many-bullets` |
| 要点 ≤5 条、每条 ≤40 字 | E1、E4 | 超过拆页或合并 | `too-many-bullets`、`bullet-too-long` |
| 口播 ≤120 字、结论 → 证据 → 所以 | E1、E4 | 能直接念；不照读页面 | `notes-too-long` |
| 单句 ≤60 汉字 | E4 | 长句拆成两句 | `sentence-too-long` |
| 数字带口径和来源 | E4、E5 | 每个数值能指到实验、公式或任务书 | 人工 |
| 避免空话、翻译腔、意义拔高 | E6 | 命中词表或模式；回读上下文 | `banned-phrase`、`ai-phrase` |
| 研究内容与创新点分开 | E4 | 两节各自回答不同问题，不互相改写 | 人工 |
| 每目标一实验、先定性后定量 | E4 | 目标与实验一一对应 | 人工 |
| 结论写达到与未达到 | E4、E5 | 不只写成绩；失败和限制有交代 | 人工 |
| 报告结构完整 | E2 | 前置、主体、结尾不缺 | 人工 |
| README 结构 | E5 | 委托 development | 委托 |

## 只能项目内约定

- 申报书章节的名称与顺序：以任务书、模板和用户 project note 为准，没有统一国标。
- 创新点与研究内容的边界：本项目要求分开，具体表述由项目定。
- 目标编号与任务书的对应关系：项目内编号体系。
- 指标口径：具体考核条件由任务书给定。
- 导师或模板给的示例：一字不改照搬，差异登记在对照表里。
- 术语层级：母课题、子课题、研究内容、研究子内容，按项目约定。
- 页片页数与顺序：按汇报时长和评审关注点定。

## 未解决

- GB/T 9704 是公文格式标准，与申报书内容规范关系弱，本轮不纳入。
- 申报书叙事没有统一国标，只能以 project note 和任务书为准；外部文章只作参考。
- 视觉、版式、配色的选择属于 R2/R3，不在文字规范内。
- README 规则已移交 development，本 skill 不重复；遇到 README 直接引用。
